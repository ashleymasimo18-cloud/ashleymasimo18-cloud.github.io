Approach

How I test

Start with the requirement

I read the requirement or acceptance criteria first, and ask when something is unclear before I write a single case.

Design the cases

I use boundary value analysis and equivalence partitioning so a small set of cases covers the real risk, and I add the negative cases people forget.

Check beneath the screen

I compare what the interface shows with what the API returns and what is stored in the database, using Postman and SQL.

Report so it can be reproduced

Each bug gets steps, environment, expected result, and actual result, so a developer can reproduce it on the first try.

Retest and regress

I verify the fix, then rerun the nearby cases to make sure nothing else broke.

Defect report

A bug that mattered

Sent invoices show the creation date instead of the sent date

Found in CRM
Steps
Save an invoice as a draft. Send it later.
Expected
The invoice shows the date it was sent.
Actual
The invoice keeps the date the draft was created.
Check
I changed the date by hand and repeated the steps to confirm the behavior was consistent, then documented it for the developers.
Impact
On a payments platform, wrong dates affect records and what clients see. This pattern would have touched tens of thousands of invoices.
